# 需求基线

## 1. 项目目标

构建一个可部署、可演示的虚拟校园 C/S 系统。6 人各自主责一个业务模块，最终交付统一登录、统一导航、统一网络协议和统一数据库下的完整应用，而不是 6 个互不相干的小程序。

## 2. 硬性技术与交付约束

- Java 开发，按教师最新说明不限制具体 Java 版本；为减少环境差异，本组统一使用已安装的 JDK 25 构建和运行。
- C/S 架构，包含客户端和服务器端。
- 客户端采用 Swing；如要改用 JavaFX，必须先验证机房环境并形成团队决议。
- Socket 通信；服务器端使用线程池处理多客户端连接。
- 网络传输对象必须实现 `java.io.Serializable`，客户端与服务器端公共类版本一致。
- 验收数据库以 Access 为准，名称为 `vCampus.accdb`；数据访问必须封装，禁止在界面中直接写 SQL。
- 统一使用 Apache Maven 3.9.16 管理项目和依赖。
- 每个类属于明确的包；接口、类和公开方法有 JavaDoc；单个 Java 文件原则上不超过 200 行。
- 最终可运行文件命名为 `vCampusClient.jar` 和 `vCampusServer.jar`。

## 3. 角色与权限基线

最低角色为 `STUDENT`、`TEACHER`、`ADMIN`。权限在服务器端校验，客户端隐藏按钮不能代替授权。

- 学生：查看/维护允许修改的个人信息、选退课、查成绩、借还书查询、购物、医院预约。
- 教师：查看教学相关信息、录入/修改所授课程成绩（以最终需求为准）。
- 超级管理员：账号、角色、子系统管理员授权和全局审计，并具有所有业务模块管理权限。
- 子系统管理员：只维护被授权模块的学籍、课程、图书、商品或医院数据，不能管理账号或扩大自己的权限。

如医院需要医务人员身份，优先增加权限 `HOSPITAL_MANAGE`，不要复制一套独立登录系统。

## 4. 六个模块的最小范围

### 4.1 用户管理

- 注册、注销、登录、登出。
- 密码不可明文存储或传输；登录失败不给出可用于枚举账号的细节。
- 角色/权限管理、账户启停、会话状态。
- 所有受保护请求在服务器端验证会话和权限。

### 4.2 学生学籍管理

- 学生、院系、专业、班级基础信息。
- 学生查看个人学籍；管理员新增、查询、修改、停用学生记录。
- 学号唯一；关键关联被使用时禁止物理删除，使用状态字段。
- 为选课、图书馆和医院提供只读的学生身份查询接口。

### 4.3 选课系统

- 课程、开课班、教师、容量、时间地点管理。
- 学生查询可选课程、选课、退选、查看课表与成绩。
- 校验重复选课、容量、时间冲突、选退课状态。
- 教师/管理员录入成绩；成绩范围和修改权限校验。

### 4.4 图书馆

- 图书信息、馆藏数量/副本、检索。
- 借阅、归还、续借（可在时间不足时降级为加分项）、借阅记录。
- 校验库存、重复借阅、借阅上限、逾期状态。
- 管理员维护图书和库存。

### 4.5 商店

- 商品分类、商品、库存、上下架和检索。
- 购物车、下单、订单查询与取消。
- 创建订单时服务器端再次校验价格和库存，并在同一事务/临界区扣减库存。
- 付款使用模拟状态流转，不接入真实支付；银行模块不在本期范围。

### 4.6 医院（选做）

- 科室、医生、排班/号源查询。
- 学生预约、取消预约、查看预约记录。
- 校验重复预约、号源容量、预约时段状态。
- 管理员维护医生和排班；诊疗记录仅做最小必要信息并限制查看权限。

## 5. 全局非功能需求

- 多客户端并发访问不会造成明显数据错乱或服务器崩溃。
- 所有用户输入在客户端做友好提示、服务器端做最终校验。
- 网络异常、数据库异常、无权限、数据不存在均返回统一错误码，客户端不得直接显示堆栈。
- 关键操作写审计日志：登录、授权、成绩变更、库存调整、预约状态变更。
- 演示账号和测试数据可一键初始化，不依赖开发者手工改库。
- 客户端、服务器端和数据库能在验收机房按说明启动。

## 6. 本期明确不做

- 真实支付、短信、邮件、第三方身份认证。
- 微服务、Web 前端、移动端和云部署。
- 不影响核心验收的复杂推荐、聊天或数据分析。
- 未经评审的额外选做模块。

## 7. 需求变更规则

新增或修改需求必须创建 Issue，写明动机、影响模块、数据库/协议影响和验收条件。跨模块或影响交付日期的变更须经组长及受影响模块负责人同意；功能冻结后只接受阻塞验收的问题修复。
