# 六人分工与任务分配

## 1. 分工原则

6 位成员各自主责 1 个业务模块。具体负责人由组长按照小组已确认的分工直接设置，公开仓库不维护姓名、学号和联系方式，以 GitHub 对应模块 Issue 的 `Assignee` 为唯一依据。

| 业务模块 | 范围 | GitHub 标签 | 负责人记录 |
|---|---|---|---|
| 用户管理 | 注册、注销、登录、登出、授权 | `module:user` | 对应模块 Issue 的 Assignee |
| 学生学籍 | 学生、院系、专业、班级和学籍维护 | `module:student` | 对应模块 Issue 的 Assignee |
| 选课系统 | 课程、开课、选退课、课表和成绩 | `module:course` | 对应模块 Issue 的 Assignee |
| 图书馆 | 图书、馆藏、借阅和归还 | `module:library` | 对应模块 Issue 的 Assignee |
| 商店 | 商品、库存、购物车和订单 | `module:shop` | 对应模块 Issue 的 Assignee |
| 医院 | 科室、医生、排班和预约 | `module:hospital` | 对应模块 Issue 的 Assignee |

组长也负责六个模块中的一个，同时承担统筹、接口协调和合并把关。六个模块必须恰好各有一位主负责人，不能一人同时占用两个业务模块，也不能出现无人负责的模块。

## 2. GitHub 统一分配流程

1. 组长使用“模块任务”模板创建六个业务模块 Epic。
2. 创建每个 Epic 时，在右侧 `Assignees` 中直接选择已确定的模块负责人。
3. 组长检查六个 Assignee 不重复，并把六个 Issue 链接发到小组群确认。
4. 每位负责人阅读范围与验收条件，在自己的 Issue 中补充计划开始时间、首个可演示时间和已知风险。
5. 如分工需要调整，相关成员先在 Issue 留下原因和交接说明，再由组长修改 Assignee；禁止只在群聊中口头交换。

分配完成的判定标准：六个模块 Issue 均只有一位主 Assignee，且 Assignee 不重复。姓名、学号和联系方式按课程分工表另行提交，不写入公开仓库。

Issue 模板中的“用户管理、学生学籍、选课系统、图书馆、商店、医院”是本阶段的六个业务模块；“公共/网络、数据库、文档/发布”只用于后续创建横向协作任务，不参与当前一人一个业务模块的初始分配。

## 3. 每个模块负责人的完整交付边界

每位负责人对所认领模块纵向负责：

- 需求：用例、角色权限、正常/异常流程和验收条件。
- 设计：界面草图、实体、表结构、服务接口、消息 action、错误码。
- 客户端：页面、输入校验、请求发送、响应展示。
- 公共层：DTO/VO、接口常量等（须走公共契约评审）。
- 服务器端：权限校验、业务规则、事务/并发处理。
- 数据层：DAO、SQL、测试数据；不得直接提交个人版二进制数据库。
- 质量：单元测试、集成测试、演示脚本、JavaDoc 和模块说明。

## 4. 公共任务认领

模块之外的公共工作单独创建 Issue，由成员自主认领，可以与自己的业务模块并行承担，也可以轮值：

- 架构协调、集成与发布。
- 数据库规范与验收库集成。
- 公共消息协议与网络联调。
- 测试计划与缺陷看板。
- Swing 公共组件与视觉规范。
- 文档目录、演示材料与提交清单。

公共任务同样以 Issue Assignee 为准。公共任务负责人负责协调和把关，不代表独自完成，全员仍须遵守公共规范并维护自己模块的相关内容。

## 5. 跨模块依赖

| 调用方 | 依赖 | 约定 |
|---|---|---|
| 所有模块 | 用户管理 | 只使用 `userId`、会话和权限接口，不自行保存密码或登录状态 |
| 选课 | 学籍 | 只读查询学生有效状态，不直接操作学籍表 |
| 图书馆 | 学籍/用户 | 校验借阅人身份；借阅数据由图书馆模块拥有 |
| 商店 | 用户 | 订单保存 `userId`；不依赖学籍表内部字段 |
| 医院 | 学籍/用户 | 预约保存 `userId/studentId`；敏感信息按权限返回 |

模块表由对应模块 Issue 的 Assignee 负责。其他模块如需数据，应请求服务接口或通过经评审的只读查询，不得复制数据或跨模块随意更新表。

## 6. 代码评审

- PR 作者邀请任意一位非作者成员进行基础评审，作者不能批准自己的 PR。
- 公共协议、数据库结构和主导航的变更，还须邀请对应公共任务 Issue 的 Assignee。
- 跨模块变更须邀请所有受影响模块的 Assignee。
- 评审人与作者有分歧时先依据需求、接口契约和测试结果讨论；仍无法确定时由组长组织短会决策。

## 7. 工作量失衡处理

每次周会比较“已验收场景数、阻塞项、剩余风险”，不只比较提交次数。某成员被阻塞超过半天应在 Issue 中标记 `status:blocked` 并公开求助。支援者可协助测试、评审或结对编程，但原 Assignee 仍对模块验收结果负责。
