# 六人分工

|---|---|---|---|---|---|
| M1 | 待填写 | 待填写 | 用户管理 | 组长、架构协调、集成与发布 | M2 |
| M2 | 待填写 | 待填写 | 学生学籍 | 数据库规范、数据库集成 | M3 |

> 公共职责是协调和把关，不代表独自完成。每位成员都要完成自己模块的客户端、公共对象、服务器端、数据访问、测试和模块文档。

## 2. 每个模块负责人的完整交付边界

每个人对自己的模块纵向负责：

- 需求：用例、角色权限、正常/异常流程和验收条件。
- 设计：界面草图、实体、表结构、服务接口、消息 action、错误码。
- 客户端：页面、输入校验、请求发送、响应展示。
- 公共层：DTO/VO、接口常量等（须走公共契约评审）。
- 服务器端：权限校验、业务规则、事务/并发处理。
- 数据层：DAO、SQL、测试数据；不得直接编辑并提交个人版二进制数据库。
- 质量：单元测试、集成测试、演示脚本、JavaDoc 和模块说明。

## 3. 跨模块依赖

| 调用方 | 依赖 | 约定 |
|---|---|---|
| 所有模块 | 用户管理 | 只使用 `userId`、会话和权限接口，不自行保存密码或登录状态 |
| 选课 | 学籍 | 只读查询学生有效状态，不直接操作学籍表 |
| 图书馆 | 学籍/用户 | 校验借阅人身份；借阅数据由图书馆模块拥有 |
| 商店 | 用户 | 订单保存 `userId`；不依赖学籍表内部字段 |
| 医院 | 学籍/用户 | 预约保存 `userId/studentId`；敏感信息按权限返回 |

模块表由模块负责人拥有。其他模块如需数据，应请求服务接口或通过经评审的只读查询，不得复制数据或跨模块随意更新表。

## 4. 评审搭档

默认采用环形评审：M1→M2→M3→M4→M5→M6→M1。公共协议、数据库结构和主导航的变更，除搭档外还须邀请对应公共职责负责人；组长自己的 PR 不能自审自合。

## 5. 工作量失衡处理

每次周会比较“已验收场景数、阻塞项、剩余风险”，不只比较提交次数。某成员被阻塞超过半天应公开求助；支援者可协助测试、评审或结对编程，但模块负责人仍对验收结果负责。不得在最后一周才暴露无法完成的模块。
