# 总体架构与接口约定

## 1. 推荐项目结构

```text
JAVA-Campus-software/
├─ pom.xml
├─ vcampus-common/       # Message、DTO/VO、枚举、错误码；客户端/服务器共用
├─ vcampus-client/       # Swing 页面、客户端服务、网络连接
├─ vcampus-server/       # 业务服务、DAO、连接处理、线程池
├─ database/
│  ├─ schema/            # 可审查、可合并的建表脚本
│  └─ seed/              # 演示/测试数据脚本或导入说明
├─ docs/
└─ release/              # 最终验收包；只在发布 PR 中更新
```

业务包统一为 `edu.seu.vcampus.common.<module>`、`edu.seu.vcampus.client.module.<module>`、`edu.seu.vcampus.server.module.<module>`；其中 `module` 取 `user`、`student`、`course`、`library`、`shop`、`hospital`。模块内部再按 `view`、`service`、`dao`、`model` 等职责拆分，一旦有业务代码后不随意改包名。

## 2. 分层职责

- View：显示、收集输入、调用客户端服务；不写 SQL，不包含服务器业务规则。
- Client Service：组装请求、调用网络客户端、把响应转换为页面可用结果。
- Common：只放双方都需要且稳定的可序列化对象、枚举和契约，不放 Swing 或数据库实现。
- Server Service：权限、校验、业务流程、事务和错误转换。
- DAO：只负责数据访问，不负责界面和网络。
- Infrastructure：Socket、线程池、连接、配置、日志、数据库连接等公共能力。

客户端模块统一通过 `ClientContext` 发送请求并共享当前会话，服务器模块统一通过 `ServerContext.sessions()` 查询 token 对应的用户和角色。业务模块不得自行保存第二套账号或绕过服务器端权限校验。

### 2.1 身份与管理员权限

- 登录页只接收账号和密码，不提供“学生/教师/管理员”身份选择；身份由服务器查询账号记录后确定。
- 基础角色为 `STUDENT`、`TEACHER`、`SUPER_ADMIN`；子系统管理员不是互斥角色，而是基础身份上的 `AdminScope` 授权。
- `SUPER_ADMIN` 负责账号生命周期、角色、子系统管理范围和审计，并具有所有业务模块的管理权限。
- 学生或教师账号可以绑定一个或多个业务范围：`STUDENT`、`COURSE`、`LIBRARY`、`SHOP`、`HOSPITAL`，且只能执行已授权模块的管理 action。
- `USER` 不是可分配的子系统范围。只有超级管理员可以管理账号和管理员授权，子系统管理员不能创建管理员或扩大自己的权限。
- 登录成功后，服务器把角色和范围放入只读 `SessionInfo`。授权发生变更时必须使该账号的旧会话失效，重新登录后生效。
- 客户端按会话隐藏无权入口只用于改善体验；所有读写 action，尤其管理 action，必须在服务器端通过 `ServerContext.sessions()` 再次校验。
- 所有已登录账号均可进入普通业务模块；每个子系统根据业务身份和 `AdminScope` 在模块内部提供模式入口。例如医院患者模式对所有账号开放，医生模式检查医生绑定，管理模式检查 `HOSPITAL` 范围。
- 管理模式的数据修改链路固定为 `Swing 管理页面 → ClientContext → 管理 Action/DTO → ServerModule 鉴权 → Service 校验 → DAO → Access`。
- 系统至少保留一个启用的超级管理员；禁止停用自己、删除自己或撤销最后一个启用超级管理员的权限。

## 3. 请求/响应契约

公共消息类至少包含：

```text
Message
  requestId: String       # 每次请求唯一，用于日志关联
  action: String          # 例如 COURSE.ENROLL
  token: String           # 未登录请求可为空
  data: Serializable      # 明确的请求 DTO，禁止随意传 Map
  success: boolean        # 响应字段
  code: String            # 统一状态/错误码
  message: String         # 可展示的简短说明
```

约定：

- action 使用 `<MODULE>.<VERB>`，如 `USER.LOGIN`、`STUDENT.GET_PROFILE`、`COURSE.ENROLL`、`LIBRARY.BORROW`、`SHOP.CREATE_ORDER`、`HOSPITAL.BOOK`。
- 每个 action 都在对应模块 Epic 正文中写明请求 DTO、响应 DTO、角色、校验和错误码。
- 管理 action 还必须写明所需 `AdminScope`；超级管理员隐式拥有全部业务范围，子系统管理员按会话中的范围判断。
- DTO 只携带业务数据，不包含 DAO、Socket、Swing 组件或数据库连接。
- 修改公共类前先建“契约变更”Issue，并在同一 PR 中修改调用方、处理方和测试。
- 公共可序列化类显式声明 `serialVersionUID`。

## 4. 统一错误码

| 前缀 | 含义 | 示例 |
|---|---|---|
| `COMMON_` | 参数、网络、服务器通用错误 | `COMMON_INVALID_ARGUMENT` |
| `AUTH_` | 登录、会话、权限 | `AUTH_FORBIDDEN` |
| `STUDENT_` | 学籍 | `STUDENT_NOT_FOUND` |
| `COURSE_` | 选课 | `COURSE_CAPACITY_FULL` |
| `LIBRARY_` | 图书馆 | `LIBRARY_NO_AVAILABLE_COPY` |
| `SHOP_` | 商店 | `SHOP_OUT_OF_STOCK` |
| `HOSPITAL_` | 医院 | `HOSPITAL_SLOT_FULL` |

服务器记录异常详情，客户端只显示安全、可理解的信息。不得把 SQL、路径、密码或堆栈放入响应。

## 5. 数据库规范

- 验收库名 `vCampus.accdb`；通过 JDBC/数据访问封装连接。
- 表名统一 `tbl<PascalCase>`，例如 `tblUser`、`tblStudent`、`tblCourseOffering`。
- 主键和外键命名统一；所有表结构先以文本脚本/数据字典评审，再由“数据库集成”公共 Issue 的 Assignee 集成验收库。
- 密码只保存带盐哈希；配置文件不提交真实密码或个人路径。
- 业务删除优先使用状态字段；已有外键关联的数据禁止直接物理删除。
- 订单扣库存、课程占容量、医院占号源等必须在服务器端原子处理；失败后不能留下半完成状态。
- 每个模块提供可重复初始化的最小演示数据和清理说明。

二进制 `.accdb` 文件只由“数据库集成”公共 Issue 的 Assignee 在发布分支/发布 PR 中统一生成和提交，日常开发通过表设计文档和脚本协作，避免 Git 无法合并数据库文件。

## 6. 网络与并发

- 服务器使用固定大小线程池，不为无限连接无控制地创建线程。
- 网络读写设置超时；客户端断开、无效消息和反序列化失败不能导致服务器退出。
- Object Stream 的创建顺序必须在双方统一，避免握手死锁。
- 共享库存/容量/号源的检查与更新使用同一服务层临界区或数据库事务策略。
- 日志至少含时间、requestId、userId、action、结果和耗时，不记录密码/完整敏感病历。

## 7. 客户端 UI 规范

- 登录后进入统一主框架，按权限显示六个模块入口。
- 页面统一字体、边距、按钮顺序、表格样式和错误提示方式。
- 耗时网络请求不得阻塞 Swing EDT；使用 `SwingWorker` 等方式执行，完成后回到 EDT 更新界面。
- 表单提供必填、格式和范围提示；清晰处理加载中、空数据、失败和成功状态。
- 每个模块至少提供一个可连续演示的主流程，避免答辩时频繁切换测试数据。

## 8. 架构决策规则

下列事项改变前必须建立决策记录：模块边界、公共 Message、数据库引擎/访问方式、认证会话、线程模型、项目目录和构建方式。决策记录写入 `docs/decisions/`，包含背景、决定、备选方案和影响。
