# 组长统筹与过程留痕

## 1. 组长的核心职责

组长不需要包办所有代码。组长最重要的工作是维护共同目标和集成节奏，让每项工作都具备：负责人、截止时间、验收条件、可复用证据。

具体职责包括：

- 维护需求边界，避免成员各自理解成六个不同项目。
- 确保六个模块和公共任务都有人负责，没有重复认领或无人认领。
- 推动公共接口、数据库规范和主界面先确定，再允许大规模并行开发。
- 每周检查可运行成果，而不是只听“代码写了多少”。
- 及时处理阻塞和跨模块冲突，控制新增需求。
- 让 Issue、PR、测试、截图和会议记录形成最终文档证据。
- 维护 `main` 可构建、可演示，组织阶段版本和最终发布。

## 2. 唯一事实来源

同一信息只在一个地方作为正式依据，其他文档通过链接引用：

| 信息 | 正式记录位置 | 用途 |
|---|---|---|
| 项目范围和验收规则 | `docs/01-需求基线.md` | 软件设计说明书、验收 |
| 模块负责人 | GitHub 模块 Issue 的 Assignee | 分工表、个人小结 |
| 任务状态和阻塞 | GitHub Issue | 进度报告、周会 |
| 实际代码变更 | Pull Request 与 Commit | 源代码说明、个人贡献 |
| 技术决策及原因 | `docs/decisions/ADR-*.md` | 设计说明书、项目总结 |
| 当前整体状态 | `docs/progress/CURRENT_STATUS.md` | 组长看板、汇报 |
| 项目事件时间线 | `docs/progress/PROJECT_LOG.md` | 项目报告、答辩 |
| 风险与解决措施 | `docs/progress/RISK_REGISTER.md` | 进度报告、经验总结 |
| 需求到测试的对应关系 | `docs/progress/TRACEABILITY.md` | 设计、测试、验收 |

群聊只用于沟通，不作为最终依据。群聊中形成的决定应在当天同步到 Issue 或 ADR。

## 3. GitHub 看板流程

所有任务按以下状态流转：

```text
Backlog → Ready → In Progress → In Review → Done
                         ↓
                      Blocked
```

- Backlog：想法或尚未明确的工作。
- Ready：范围、依赖和验收条件清楚，可以领取。
- In Progress：已有 Assignee，正在开发。
- In Review：已创建 PR，等待评审或联调。
- Blocked：超过半天无法推进，写明原因和需要谁帮助。
- Done：PR 已合并，测试和文档证据齐全，而不是“本地写完”。

每个 Issue 至少包含：目标、范围、验收条件、负责人、截止时间、依赖、测试方法。一个 Issue 最好控制在半天到两天内完成；模块 Epic 再拆成多个小 Issue。

## 4. 推荐会议节奏

### 每次开发开始前：10 分钟站会

每人只回答：上次完成的可验收结果、下一步、阻塞。组长不在站会上讨论长技术问题，争议另开短会。

### 每周中段：集成检查

- 拉取最新 `main`，运行构建和测试。
- 六个模块至少展示当前最小可运行结果。
- 提前发现公共 DTO、数据库和导航冲突。
- 将问题建立 Issue，不在个人电脑中秘密修复。

### 每周结束：30 分钟周会

- 对照阶段目标检查完成情况。
- 更新当前状态、风险表和追踪表。
- 确认下周每个模块的一个主要交付物。
- 选出本周可用于答辩/文档的截图、测试结果和关键决策。
- 形成 `docs/progress/YYYY-MM-DD-week-N.md`。

## 5. 阶段门禁

### 门禁 A：开始并行开发前

- 六个模块均完成自主认领。
- 所有人环境检查通过。
- Maven 三模块骨架、最小 Socket 请求、数据库连接可运行。
- Message、错误码、权限和数据库命名规范完成评审。

### 门禁 B：核心功能完成

- 六模块均有至少一个客户端到服务器到数据库的完整流程。
- 主流程及关键异常流程可演示。
- 跨模块调用通过公共接口，不直接修改其他模块的表。

### 门禁 C：功能冻结

- 六模块最小范围全部完成。
- P0/P1 缺陷清零。
- 自动测试、演示数据、模块说明齐全。
- 冻结后不增加新功能，只修复影响验收的问题。

### 门禁 D：最终发布

- 全新环境按说明部署成功。
- 客户端、服务器端、数据库和文档材料齐全。
- 软件设计说明书中的接口、表和界面与实际代码一致。
- 至少两次完整答辩彩排。

## 6. 过程证据如何转为最终材料

| 过程记录 | 最终可复用到 |
|---|---|
| 需求 Issue、验收条件 | 需求分析、功能说明、验收表 |
| ADR、接口和表结构评审 | 软件设计说明书、关键技术 |
| PR 描述、提交记录 | 源代码说明、分工表、个人小结 |
| 周会、阶段版本和燃尽情况 | 小组进度计划/检查报告 |
| 测试用例、失败记录、修复 PR | 测试计划、测试分析报告 |
| 风险表、阻塞及解决措施 | 项目经验、存在问题、团队协作总结 |
| 界面截图和演示脚本 | 系统使用说明、PPT、答辩 |
| Release 文件和部署验证 | 提交清单、安装运行说明 |

每个模块负责人都应保存：一张模块结构图、一份表结构、一份接口/action 清单、主流程截图、异常流程截图、测试结果、关键问题与解决办法。缺少这些证据时，功能不能视为完全交付。

## 7. 组长每周看板

组长每周只需要重点关注以下指标：

- 六个模块中已认领/未认领数量。
- 本周计划 Issue 完成率。
- `main` 最近一次构建结果。
- 六模块已打通纵向流程的数量。
- P0/P1 缺陷数量。
- 阻塞超过半天的 Issue 数量。
- 尚未评审的公共契约/数据库变更。
- 本周是否产生可复用的文档、测试和截图证据。

发现延期时先缩减非核心功能、安排结对和解决阻塞，不直接替成员完成全部工作。

## 8. 变更控制

教师要求变化、数据库/协议变化、模块范围变化必须创建 Issue 或 ADR，写明原因、影响范围和迁移办法。口头决定当天未落库，视为尚未正式决定。

组长每周将 GitHub 中的新进展同步到 `CURRENT_STATUS.md` 和 `PROJECT_LOG.md`。在本 Codex 任务中告知新的进展后，也应同步更新这些文件并推送到仓库。
