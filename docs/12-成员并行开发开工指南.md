# 成员并行开发开工指南

## 1. 什么时候可以开工

公共开发基线 PR 合并到 `main`，且成员本机执行 `mvn clean verify` 成功后即可开工。Access/JDBC 尚未完成不会阻塞第一条端到端功能，但在数据库 ADR 通过前只能先使用接口、内存演示数据和文本数据字典，不得各自引入其他数据库。

商店负责人尚未接受邀请不阻塞其余五个模块；商店模块入口和文档位置先保留，成员加入后再分配 Epic 并开分支。

## 2. 每位成员只修改自己的区域

把 `<module>` 替换为 `user`、`student`、`course`、`library`、`shop` 或 `hospital`：

```text
vcampus-common/src/main/java/edu/seu/vcampus/common/<module>/
vcampus-client/src/main/java/edu/seu/vcampus/client/module/<module>/
vcampus-server/src/main/java/edu/seu/vcampus/server/module/<module>/
database/schema/<module>.md
docs/modules/<module>.md
```

不要自行修改以下共享文件：

- `CampusServer.java`、`CampusClient.java`、`Request.java`、`Response.java`。
- `MainFrame.java`、`ServerModules.java`、`ClientModules.java`。
- 根 `pom.xml` 和其他模块负责人的目录。

确实需要修改共享文件时，先在自己的 Epic 留言说明原因，由组长确认后单独建立公共契约 PR。

## 3. 第一次拉取与建分支

在 IDEA 的终端中执行：

```powershell
git switch main
git pull origin main
mvn clean verify
git switch -c feature/<module>-first-slice
```

分支示例：`feature/course-first-slice`。不要直接在 `main` 上开发。

## 4. 第一条端到端功能由负责人提出

第一轮的固定要求不是指定某个功能，而是每个模块至少完成一条范围内、低依赖、可演示的端到端流程，使界面能够经过 Socket 调用服务器并显示结果。下表只是帮助快速开工的推荐候选，不是不可修改的任务命令：

| 模块 | 推荐候选 | action 示例 |
|---|---|---|
| 用户管理 | 登录表单与登录响应原型 | `USER.LOGIN` |
| 学生学籍 | 按学号查看学籍 | `STUDENT.GET_PROFILE` |
| 选课系统 | 查询可选课程 | `COURSE.LIST_AVAILABLE` |
| 图书馆 | 按关键字检索图书 | `LIBRARY.SEARCH_BOOKS` |
| 商店 | 查询上架商品 | `SHOP.LIST_PRODUCTS` |
| 医院 | 查询医生排班/号源 | `HOSPITAL.LIST_SLOTS` |

负责人可以选择同一模块范围内的其他功能，但须先在模块 Epic 留言写明：用户故事、拟用 action、页面、请求/响应 DTO、测试方式和跨模块依赖。满足“范围内、工作量适中、不新增未经评审的公共依赖、可独立验收”即可由组长确认，无须六个人做成相同形式。

公共基线已经提供可替换的开发期登录和会话，因此其他模块无需等待用户数据库即可测试登录后请求。用户模块负责人仍须负责最终 Access 用户 DAO、密码策略、账户状态和权限；第一轮选择其他流程时，应在 Epic 中说明正式认证的预计交付时间。其他模块第一轮优先选择查询型流程，是为了降低数据库尚未完成造成的阻塞，不代表最终只能做查询。

第一轮可以使用服务器内存中的虚构演示数据，目的是先证明 View → Client → Request → Server Handler → Response → View 的链路。临时数据必须集中在模块自己的 server 包中，并明确标记后续由 DAO 替换。

## 5. 第一轮 PR 必须包含

- 在 `docs/modules/<module>.md` 填写负责人选定的一个用例、角色、正常/异常流程。
- 在 `database/schema/<module>.md` 提交第一版数据字典。
- 在 common 的本模块目录定义 action 常量，以及明确类型的可序列化请求/响应 DTO；禁止使用随意的 `Map`。
- 在 server 的本模块入口注册 handler，并在本模块 service 中完成参数校验。
- 受保护 handler 使用共享 `ServerContext.sessions()` 校验 token/角色；客户端用 `ClientContext.send` 自动携带 token。
- 将 client 的本模块占位页替换成可操作 Swing 页面；网络操作使用 `SwingWorker`。
- 至少一个自动测试，并保证 `mvn clean verify` 为 `BUILD SUCCESS`。
- PR 关联自己的模块 Epic，附运行截图，并邀请至少一位非作者评审。

## 6. 推荐提交顺序

```text
docs(<module>): add first use case and contract draft
feat(<module>): add action and serializable DTOs
feat(<module>): implement first server handler
feat(<module>): implement first Swing flow
test(<module>): cover first end-to-end flow
```

允许一个 PR 中有多次小提交，不需要把未完成代码提前合并。

## 7. 组长每天检查

- `main` 是否仍能 `mvn clean verify`。
- 每个 Epic 是否有下一步、阻塞和 PR 链接。
- 是否有人修改其他模块目录或共享核心文件。
- action 名、DTO、表名是否互相冲突。
- UI、服务、数据字典和测试是否同步，而不是只做界面。

## 8. 开工完成标志

当六个模块都至少合并一条经各自 Epic 确认的端到端功能后，项目进入“业务开发阶段”；在此之前仍属于“并行开发启动阶段”。数据库 ADR、认证会话和主导航权限仍由公共任务单独推进，不能把临时演示实现写成最终完成状态。
