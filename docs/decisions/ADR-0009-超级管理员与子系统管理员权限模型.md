# ADR-0009：区分超级管理员与子系统管理员

- 状态：通过（权限基础已实现，用户管理页面待实现）
- 日期：2026-08-28
- 决策范围：登录、会话、用户管理和六模块服务器鉴权

## 背景

课程需求把多类维护人员统称为“管理员”，但账号管理与医院、图书、课程等业务维护的风险和职责不同。若只保留一个 `ADMIN` 角色，任何业务管理员都会获得修改账号、分配权限和操作其他模块的能力；若由登录页让用户选择身份，又会把权限决定交给客户端，无法形成安全边界。

## 决定

### 角色与范围

- 使用 `STUDENT`、`TEACHER`、`MODULE_ADMIN`、`SUPER_ADMIN` 四种基础角色。
- `SUPER_ADMIN` 是系统最高权限：管理账号生命周期、角色、子系统范围和审计，并可执行所有业务模块管理 action。
- `MODULE_ADMIN` 是子系统管理员，必须绑定至少一个 `AdminScope`，只能管理被授予的 `STUDENT`、`COURSE`、`LIBRARY`、`SHOP` 或 `HOSPITAL` 模块。
- `USER` 不作为可分配范围；账号和管理员授权只能由超级管理员管理。

### 身份确定时机

1. 超级管理员创建账号或修改授权时，把角色与范围保存到用户数据中。
2. 登录页只提交账号和密码，不显示身份选择框。
3. 服务器验证凭据后加载角色与范围，签发包含只读权限快照的 `SessionInfo`。
4. 客户端据此显示模块入口；服务器对每个管理 action 再次查询会话并校验范围。
5. 角色、范围、状态或密码发生变化时，服务器使该账号全部旧会话失效；重新登录后使用新权限。

### 权限保护规则

- 子系统管理员不能查看账号列表、创建管理员、修改角色、分配范围或扩大自己的权限。
- 至少保留一个启用的超级管理员；禁止停用自己、删除自己或撤销最后一个启用超级管理员。
- 隐藏客户端按钮不是安全措施。无权请求必须由服务器返回 `AUTH_FORBIDDEN`，未登录返回 `AUTH_REQUIRED`。
- 管理员不能读取用户原密码；只能触发安全的密码重置流程。

## 备选方案

### 只有一个 `ADMIN` 角色

实现最简单，但无法区分系统账号管理与业务维护，任一管理员越权后影响全系统，未采用。

### 为每个模块增加固定角色，如 `HOSPITAL_ADMIN`

枚举直观，但多模块管理员需要组合角色，新增模块还要修改角色枚举和大量分支，未采用。

### 登录页由用户选择身份

界面看似清晰，但客户端输入不能证明权限；同一账号还可能伪装为更高角色，未采用。

### 超级管理员只管账号，不拥有业务管理权限

更符合最小权限原则，但课程项目把超级管理员定义为最高权限且需要统一验收入口。当前采用全业务管理能力；若后续希望职责隔离，应新增独立平台管理员策略而不是静默改变本 ADR。

## 影响与迁移

- 原 `ADMIN` 演示角色迁移为 `SUPER_ADMIN`；为 `STUDENT`、`COURSE`、`LIBRARY`、`SHOP`、`HOSPITAL` 五个业务范围分别提供一个开发期子系统管理员账号。
- `SessionInfo` 增加不可变 `adminScopes`，并提供 `canManageUsers()`、`canAdminister(moduleId)`。
- 子系统管理 action 应使用 `ServerContext.sessions().canAdminister(token, moduleId)` 或等价服务器校验。
- 客户端每次登录都按新会话重建导航，避免前一个账号的入口泄露给后一个账号。
- 客户端通过 `ModuleViewMode.USER / MANAGEMENT` 明确页面模式；模块可以复用查询页，但只能在管理模式显示维护入口。
- Access 用户表与范围关联表按 `database/schema/user.md` 实现；正式 DAO 接入前继续使用可替换内存认证。
