## 一、本轮目标

每位已加入仓库的模块负责人，在自己的模块内完成 **1 条小而完整、可以现场演示的端到端功能链路**：

```text
Swing 页面 → ClientContext → Request/DTO → Socket
→ Server Handler/Service → Response/DTO → Swing 页面显示结果
```

本轮重点是证明公共架构和自己的模块可以协同工作，不追求一次把模块全部写完。

具体功能由模块负责人自行提出，不固定死。建议优先选择低依赖、容易验证的查询型功能，例如：查询学籍、查询可选课程、检索图书、查询商品、查询医院号源等。用户模块可选择账户信息查询、注册原型或正式认证方案中的一个小切片。也可以选择同模块内其他功能，但应满足：

- 属于本人负责模块的需求范围；
- 3—4 天内能独立完成和演示；
- 不新增未经评审的公共依赖；
- 同时包含界面、通信、服务器处理、返回显示和测试；
- 临时数据集中放在本模块 server 包，并注明以后由 DAO 替换。

提前完成后可以增加同一流程中的一个异常场景或一个紧密相关的小操作，但不要为了数量扩大范围。宁可完整完成 1 条链路，也不要留下 3 个只能点开、不能联调的半成品页面。

## 三、开始开发

先在自己的模块 Epic 留言，写清：用户故事、功能目标、页面、Action、请求/响应 DTO、正常与异常流程、权限、测试方法、依赖和风险。组长确认没有公共冲突后，在 IDEA 终端运行：

```powershell
git switch main
git pull origin main
mvn clean verify
git switch -c feat/<module>-<issue编号>-<功能简述>
```

例如：

```powershell
git switch -c feat/library-6-search-books
```

必须从最新 `main` 建立分支。构建未通过时先解决环境或基线问题，不带错开工。

## 四、统一开发规则

1. 禁止直接在 `main` 编写或推送业务代码；组长也遵守相同规则。
2. 一个具体功能对应一个 Issue、一个功能分支和一个 Pull Request，不使用长期个人总分支。
3. 原则上只修改自己的五个区域：

   ```text
   vcampus-common/src/main/java/edu/seu/vcampus/common/<module>/
   vcampus-client/src/main/java/edu/seu/vcampus/client/module/<module>/
   vcampus-server/src/main/java/edu/seu/vcampus/server/module/<module>/
   docs/modules/<module>.md
   database/schema/<module>.md
   ```

4. 不自行修改根 `pom.xml`、公共 Request/Response、网络框架、主导航、模块注册表和其他成员目录。确需修改时先在 Epic 说明，由组长建立或批准公共契约任务。
5. 使用现有 `ClientContext` 和 `ServerContext.sessions()` 共享登录状态；不要重写登录窗口、另存 token 或依赖内存认证内部实现。
6. Action 使用模块前缀；请求和响应使用明确、可序列化的 DTO，不用随意的 `Map` 代替数据结构。
7. 权限必须由服务器端校验；只隐藏 Swing 按钮不算权限控制。
8. Swing 网络调用使用 `SwingWorker` 等后台方式，不能阻塞界面线程。
9. 每个接口、类和公开方法补 JavaDoc；单个 Java 文件原则上不超过 200 行。
10. 不提交 `.idea`、`target`、个人 `.accdb`、密码、密钥、绝对路径和无关格式化改动。
11. 公共契约、数据字典、模块设计和代码保持同步，不能只交页面。

## 五、本轮完成标准

一名成员完成本轮任务，必须同时满足：

- 模块 Epic 已记录选定用例和验收条件；
- 模块设计文档已补用户、角色、正常与异常流程；
- 数据字典已提交第一版；
- common 中有 Action 和明确类型的请求/响应 DTO；
- server 中完成 handler、service、参数校验及必要的登录/角色校验；
- client 中完成可操作的 Swing 页面，并能显示服务器返回结果；
- 至少有 1 个自动测试；
- 本机运行 `mvn clean verify` 为 `BUILD SUCCESS`；
- PR 关联 Issue，附测试结果和界面截图，并邀请至少 1 位非作者评审。

本轮完成不代表整个业务模块完成；它只代表该模块的第一条完整开发链路已经建立。

## 六、Pull Request 前自查

```powershell
git switch main
git pull origin main
git switch <自己的分支>
mvn clean verify
git status
```

确认测试失败数和错误数均为 0，再推送分支并创建 PR。作者不能批准自己的 PR；处理完评审意见后由组长或获授权成员合并。

## 七、阻塞如何报告

遇到以下情况时，不要各自在公共代码中尝试不同方案，应立即在模块 Epic 留言并联系组长：

- 需要修改共享核心文件；
- Action、DTO、表名与其他模块冲突；
- 依赖尚未确定的 Access/JDBC 方案；
- 需要跨模块直接读取对方 DAO 或界面；
- `main` 自身无法构建，或公共 PING/登录链路失败。

留言格式：`当前做到哪里 / 具体错误 / 已尝试什么 / 需要谁协助 / 是否影响本轮截止时间`。
